Security & compliance · AWS and Azure

Security controls need evidence, not just intentions.

A cloud-control reference model showing how policy, identity, configuration checks and operational evidence can support audit readiness.

Reference design · not a client project

The problem

Why this matters.

A prospective customer asks for proof of access controls and data protection. Your team has tools in place, but the evidence is scattered.

The situation

A software provider operates workloads across AWS or Azure and needs a disciplined way to establish controls, detect exceptions and retain reviewable records.

The goal

A proposed control-to-evidence workflow with clear owners, periodic reviews and remediation tracking.

Technical scope
AWS IAM / CloudTrail / ConfigAzure RBAC / Policy / Activity LogKMS / Key VaultControl mappingsEvidence retention

The approach

Four design principles.

01

Start with scope

Identify the applicable workload, data, contractual obligations and control owners before selecting tools.

02

Turn policy into checks

Translate requirements into documented configurations, detective controls, approval workflows and exceptions.

03

Preserve traceable evidence

Record changes, access reviews, control assessments and remediation outcomes with suitable access and retention controls.

04

Keep assurance independent

Technical evidence supports review, but an engineer does not certify compliance or issue an independent audit opinion.

The judgement calls

Trade-offs, not just tools.

Every choice has a cost. Here is what each decision buys, and what we’d check before committing to it.

01

Use native cloud controls first

Why it can fit

AWS Config and CloudTrail, or Azure Policy and Activity Log, can provide useful configuration and activity signals.

What we’d check

Coverage, setup, retention and cross-account/subscription scope must be verified; tools alone do not establish compliance.

02

Track exceptions explicitly

Why it can fit

A documented risk acceptance or remediation ticket is easier to review than an unexplained failed policy.

What we’d check

A tracking process requires owners and scheduled follow-through.

03

Separate technical evidence from audit judgment

Why it can fit

Keep evidence reproducible while allowing qualified assessors to form independent conclusions.

What we’d check

Framework interpretations and legal obligations require subject-matter review.

Proving it

How we’d validate it.

This is the test plan, not a record of tests already run.

Evidence

Identity & access

Role assignments, privileged access reviews, approved exceptions and access removal records.

Evidence

Cloud change history

Configuration snapshots, policy findings, action logs and remediation tickets.

Evidence

Data protection

Encryption configuration, key permissions, backup settings and data-flow documentation.

  1. Create a scoped control inventory and identify each control owner.
  2. Validate that important configuration changes produce records and alertable findings.
  3. Confirm log collection, permissions, retention and the gaps in evidence coverage.
  4. Run a mock technical evidence request with a reviewer; capture missing artifacts and close the gaps.
What this is and isn’t: A technical control and evidence design—not legal advice, a HIPAA certification, ISO 27001 certification, SOC 2 report, or formal independent audit.

Next milestone: The next proof milestone is an isolated AWS/Azure lab with test controls, deliberate violations and recorded evidence/recovery workflows.
